## 🎯 1. Core DBMS Concepts Applied in the System

### 1.1 Keys & Constraints
- **Primary Key (`id`)**: A surrogate primary key generated automatically via `bigint generated by default as identity`. Guarantees entity integrity and uniquely identifies every row.
- **Candidate / Unique Key (`register_no`)**: Enforces `UNIQUE` constraint ensuring no two students share the same register number across the institution.
- **Domain & Check Constraints**:
  - `year int not null check (year between 1 and 4)` ensures only valid 4-year undergraduate values can be stored in the database.
  - `not null` constraints on `name`, `register_no`, `department`, and `email` prevent null anomalies.

### 1.2 ACID Properties
- **Atomicity**: An operation (such as adding or updating a student) executes completely or aborts entirely with no partial state saved.
- **Consistency**: Database transitions from one valid state to another. Constraints (`CHECK (year BETWEEN 1 AND 4)`, `UNIQUE`, `NOT NULL`) are strictly enforced at the database engine level.
- **Isolation**: PostgreSQL uses Multi-Version Concurrency Control (MVCC) with Read Committed isolation level by default. Concurrent modifications by multiple users do not interfere with one another.
- **Durability**: Transactions committed to PostgreSQL are written to Write-Ahead Logs (WAL) and stored durably on persistent non-volatile disk.

### 1.3 Row Level Security (RLS) & Client Access
- PostgreSQL Row Level Security (RLS) is enabled on the `students` table.
- A public access policy `create policy "Public full access to students" on public.students for all using (true) with check (true);` permits the web application's anonymous key (`anon`) to execute SELECT, INSERT, UPDATE, and DELETE operations seamlessly without authentication overhead.

### 1.4 Database Normalization
The `public.students` table satisfies:
- **1NF (First Normal Form)**: All attributes contain atomic values (single values per cell); each row has a primary key.
- **2NF (Second Normal Form)**: In 1NF and all non-key attributes are fully functionally dependent on the primary key (`id`).
- **3NF (Third Normal Form)**: In 2NF and has no transitive dependencies (`non-key -> non-key`). Student details depend strictly on student identity.

### 1.5 Indexing & Query Performance
- `idx_students_register_no`: An indexed B-tree index on `register_no` ensures that search queries and uniqueness checks execute in \(O(\log n)\) rather than sequential full-table scans \(O(n)\).
- `idx_students_name`: Speeds up prefix and substring matching during live search.

## 💻 2. Essential SQL Queries

### Data Definition Language (DDL)
```sql
-- Create table with constraints
create table public.students (
    id bigint generated by default as identity primary key,
    register_no text not null unique,
    name text not null,
    department text not null,
    year int not null check (year between 1 and 4),
    email text not null,
    created_at timestamp with time zone default timezone('utc'::text, now()) not null
);

-- Indexes
create index idx_students_register_no on public.students(register_no);
create index idx_students_name on public.students(name);
```

### Data Manipulation Language (DML)
```sql
-- CREATE (Insert Student)
insert into public.students (register_no, name, department, year, email)
values ('21CS101', 'Alice Johnson', 'Computer Science & Engineering', 3, 'alice@school.edu');

-- READ (Select Students)
select id, register_no, name, department, year, email, created_at
from public.students
where register_no ilike '%CS%' or name ilike '%Alice%'
order by created_at desc;

-- UPDATE (Modify Student)
update public.students
set year = 4, department = 'Artificial Intelligence & Data Science'
where id = 1;

-- DELETE (Remove Student)
delete from public.students
where id = 1;
```

## ❓ 4. Frequently Asked Viva Questions & Model Answers

### Q1: What makes `register_no` a candidate key?
**Answer**: A candidate key is a minimal superkey that can uniquely identify any tuple in the relation. `register_no` satisfies uniqueness and non-nullity, making it an alternate candidate key while `id` serves as the primary key.

### Q2: How does PostgreSQL enforce the `CHECK (year BETWEEN 1 AND 4)` constraint?
**Answer**: During every `INSERT` and `UPDATE` transaction, PostgreSQL evaluates the boolean expression. If the expression evaluates to `FALSE`, the transaction immediately aborts and rolls back with a `check_violation` error, preserving consistency.

### Q3: What is the purpose of the B-Tree index on `register_no`?
**Answer**: Without an index, searching for a register number requires a full table scan of \(O(n)\). With a B-Tree index, the database traverses balanced tree nodes in \(O(\log n)\) time complexity, drastically reducing I/O disk reads.
