## 🎯 1. Core DBMS Concepts Applied in the System

### 1.1 Keys & Constraints
- **Primary Key (`id`)**: A surrogate primary key generated automatically via `bigint generated by default as identity`. Guarantees entity integrity and uniquely identifies every row.
- **Foreign Key (`teacher_id`)**: References `auth.users(id)` in Supabase Auth. Enforces **Referential Integrity** with `ON DELETE CASCADE` (if a teacher account is removed, all associated student records are automatically purged to prevent orphaned records).
- **Composite Unique Key (`UNIQUE (teacher_id, register_no)`)**:
  - Enforces that within a given teacher's class, no two students can share the same Register Number.
  - Allows different teachers/departments to reuse registration numbers if necessary without collision.
- **Domain & Check Constraints**:
  - `year int not null check (year between 1 and 4)` ensures only valid 4-year undergraduate values can be entered.
  - `not null` constraints on `name`, `register_no`, `department`, and `email` prevent null anomalies.

### 1.2 ACID Properties
- **Atomicity**: An operation (such as adding or updating a student) executes completely or aborts entirely with no partial state saved.
- **Consistency**: Database transitions from one valid state to another. Constraints (`CHECK (year BETWEEN 1 AND 4)`, `UNIQUE`, `NOT NULL`) are strictly enforced at the database engine level.
- **Isolation**: PostgreSQL uses Multi-Version Concurrency Control (MVCC) with Read Committed isolation level by default. Concurrent modifications by multiple teachers do not interfere with one another.
- **Durability**: Transactions committed to Supabase PostgreSQL are written to Write-Ahead Logs (WAL) and stored durably on persistent non-volatile disk.

### 1.3 Row Level Security (RLS) vs Traditional Application-Level Filtering
- **Traditional Filter**: Application passes `WHERE teacher_id = ?`. If an attacker bypasses the client or accesses the REST API directly, they can manipulate or leak other teachers' students.
- **PostgreSQL Row Level Security (RLS)**: Security policies are enforced directly in the database engine kernel:
  ```sql
  create policy "Teachers can select own students"
      on public.students for select to authenticated
      using (auth.uid() = teacher_id);
  ```
  Even with direct database/API access, the database engine verifies that the authenticated JSON Web Token (JWT) matches `teacher_id = auth.uid()`.

### 1.4 Database Normalization
The `public.students` table satisfies:
- **1NF (First Normal Form)**: All attributes contain atomic values (single values per cell); each row has a primary key.
- **2NF (Second Normal Form)**: In 1NF and all non-key attributes are fully functionally dependent on the primary key (`id`).
- **3NF (Third Normal Form)**: In 2NF and has no transitive dependencies (`non-key -> non-key`). Student details depend strictly on student identity.

### 1.5 Indexing & Query Performance
- `idx_students_teacher_id`: An indexed B-tree index on `teacher_id` ensures that RLS queries and `SELECT` filtering by teacher execute in \(O(\log n)\) rather than sequential full-table scans \(O(n)\).
- `idx_students_register_no`: Accelerates search queries on registration numbers.

## 💻 2. Essential SQL Queries

### Data Definition Language (DDL)
```sql
-- Create table with constraints
create table public.students (
    id bigint generated by default as identity primary key,
    register_no text not null,
    name text not null,
    department text not null,
    year int not null check (year between 1 and 4),
    email text not null,
    teacher_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
    created_at timestamp with time zone default timezone('utc'::text, now()) not null,
    constraint unique_teacher_student_register_no unique (teacher_id, register_no)
);

-- Indexes
create index idx_students_teacher_id on public.students(teacher_id);
create index idx_students_register_no on public.students(register_no);
```

### Data Manipulation Language (DML)
```sql
-- CREATE (Insert Student)
insert into public.students (register_no, name, department, year, email, teacher_id)
values ('21CS101', 'Alice Johnson', 'Computer Science & Engineering', 3, 'alice@school.edu', auth.uid());

-- READ (Select Students)
select id, register_no, name, department, year, email, created_at
from public.students
where register_no ilike '%CS%'
order by created_at desc;

-- UPDATE (Modify Student)
update public.students
set year = 4, department = 'Artificial Intelligence & Data Science'
where id = 1 and teacher_id = auth.uid();

-- DELETE (Remove Student)
delete from public.students
where id = 1 and teacher_id = auth.uid();
```

## ❓ 4. Frequently Asked Viva Questions & Model Answers

### Q1: Why use a Composite Unique Constraint on `(teacher_id, register_no)`?
**Answer**: In real-world educational institutions, each teacher manages their own batch of students. Enforcing `UNIQUE (teacher_id, register_no)` prevents a teacher from accidentally registering the same student ID twice, while still allowing the system to scale across independent classrooms or semesters without global key collisions.

### Q2: What is the difference between RLS and an application-level `WHERE` clause?
**Answer**: An application-level `WHERE` clause relies completely on client and server-side code discipline. If an endpoint is vulnerable to SQL injection, missing filters, or unauthorized API calls, unauthorized data is exposed. RLS embeds the access control rules directly inside PostgreSQL's query execution engine; unauthorized rows are filtered out by the database engine itself before query results leave the database.

### Q3: How does `ON DELETE CASCADE` support referential integrity?
**Answer**: When a record in the parent table (`auth.users`) is deleted, `ON DELETE CASCADE` automatically deletes all child rows in `public.students` referencing that user's ID. This prevents "orphaned rows" which violate relational integrity and waste storage.

### Q4: What data structure does PostgreSQL use for indexing?
**Answer**: PostgreSQL uses B-Trees (Balanced Trees) as its default index structure. A B-Tree maintains sorted data and provides logarithmic \(O(\log n)\) search, sequential access, insertion, and deletion times.

### Q5: What role does the JWT (JSON Web Token) play in Supabase?
**Answer**: When a teacher logs in, Supabase issues a cryptographically signed JWT containing their `sub` (UUID). On every request, this token is sent in the `Authorization: Bearer <token>` header. PostgreSQL verifies the signature and extracts `auth.uid()`, dynamically applying RLS rules for that transaction.
